> 一句话：这篇文章给的是**判据**，不是架构图。九条特征里没有一条在说"服务要小"。

## 三行判断

1. "micro" 指的是**边界**而不是代码量 —— 判断标准是能不能独立部署、独立演进，不是多少行。
2. 九条特征里真正互相咬合的是三条：围绕业务能力构建、去中心化数据管理、设计为可失败。其余六条是它们的推论或前提。
3. 这篇写于 2014 年，它推荐的"基础设施自动化"今天已经是默认值，所以真正还难做到的只剩**去中心化数据管理**。

## 它讲清楚了

- 服务边界应该按**业务能力**切，而不是按技术分层切（不是"一个 service 层一个服务"）
- 通信用轻量机制（HTTP/REST 之类），避免把 ESB 那套智能管道搬回来
- 去中心化治理：团队自己选技术栈、自己养自己的服务，而不是一个架构组统一裁决
- 去中心化数据管理：每个服务管自己的数据，**不做跨服务的共享库**
- "设计为可失败"：服务随时会挂，调用方要能降级

## 它没讲 / 我觉得不对

- **没讲清楚"多小算小"。** 原文刻意回避了这个问题，只说"能独立部署"。实际落地时这句话会被解读成任何东西，这是后来"分布式单体"泛滥的根源。
- **对跨服务查询几乎没给方案。** 去中心化数据管理一旦执行，跨服务的聚合查询就必须靠 API 组合或数据冗余，原文一笔带过。这一块后来被 CQRS / 数据同步 / 宽表各自补了一部分，但没有统一答案。
- 2014 年的语境里"自动化"很贵，所以它被列为特征；今天这条已经退化成前提条件，不值得再当区分度。

## 可复用

判据可以压成三个问题，拆服务前先自问：

```
1. 它能不能独立部署？            → 不能，就不是一个服务
2. 它有没有独立的数据所有权？    → 没有，将来一定是分布式事务
3. 它挂了，调用方降级方案是什么？ → 说不出来，就别拆
```
